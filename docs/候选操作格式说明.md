# 候选操作格式说明（升级第二阶段：理解层）

写作日期：2026-09-10。对应 [agent_task_orchestration_总体技术方案.md](agent_task_orchestration_总体技术方案.md) §4.1「模型只输出候选操作」与 [升级方案_通俗解读版.md](升级方案_通俗解读版.md) 9.2 第 1 条。本文是第二阶段的交付物之一：**模型被允许输出哪几种操作，每个字段怎么写，程序拿到之后怎么处理。**

一句话概括这次改动：**模型只提建议，程序做决定。** 模型不再生成可执行计划，它输出的东西被限制在下面这几张枚举表里；任何表外的内容（自造技能、正式文件路径、Python 代码）都会在 [core/agent/understanding/operations.py](../core/agent/understanding/operations.py) 被判为无效，不做「删掉后继续说计划有效」的宽松解析。

## 2. 整体形状

模型必须返回**一个 JSON 对象**，不带任何解释文字或代码块标记：

```json
{
  "operations": [
    {
      "op": "create",
      "label": "A",
      "target_ref": "武汉",
      "capability": "full_lst",
      "patches": {
        "region": {"action": "set", "value": "武汉", "evidence": "武汉 7 月"},
        "time":   {"action": "set", "value": "7 月",  "evidence": "武汉 7 月"}
      },
      "missing": [],
      "ambiguity": [],
      "evidence": "武汉 7 月"
    }
  ],
  "shared_modifiers": [
    {
      "patches": {"time": {"action": "set", "value": "2025 年"}},
      "applies_to": ["A", "B"],
      "evidence": "都是 2025 年"
    }
  ],
  "note": "一句话说明理解结果"
}
```

`operations` 数组上限 **8 条**：超过即整批判无效，防止模型用笛卡尔积式输出一次造出几十个任务。

## 3. 允许的操作类型（`op`）

| 取值 | 含义 | 程序拿到之后做什么 |
|---|---|---|
| `create` | 新建一个任务目标 | 建任务草稿，按能力检查必需信息 |
| `set` | 给已有目标补值或改值 | 绑定目标 → 应用补丁 → 递增任务版本 |
| `clear` | 用户否定了某个信息 | 清空该字段并**留下否定记录** |
| `correct` | 更正（否定旧值 + 给出新值） | 等价于 clear + set，同一事务内完成 |
| `answer` | 回答一个待答问题 | 走「消费答案」事务，答案一次消费 |
| `continue` | 继续某个已有任务 | 绑定唯一任务；不唯一则追问 |
| `retry` | 重试某个已有任务 | 同上 |
| `cancel` | 取消某个已有任务 | 同上，任务转为已取消 |
| `priority` | 调整某个任务的先后顺序 | 只改调度信息，科学快照不变 |
| `reply_only` | 只回答，不动任何任务 | 转纯对话，不建任务 |

前八种统称**生产类操作**。Chat 只读模式在代码层面（`understander.enforce_chat_mode`）把它们全部剔除，只保留 `reply_only`——这是权限边界，不是一段提示词。

## 4. 允许的能力（`capability`）

| 取值 | 含义 | 编译前最低必要信息 | 映射到旧执行链 |
|---|---|---|---|
| `query` | 只回答问题 | 无 | 不产生任何步骤 |
| `search` | 只搜索影像 | 研究区、时间 | 数据获取（只搜不下） |
| `download_subset` | 只下载点名的数据集合 | 研究区、时间、数据集合 | 数据获取 |
| `preprocess` | 只做预处理 | 研究区 | 预处理 |
| `train` | 只做训练 | 研究区 | 预处理 → TTRI → 训练 |
| `full_lst` | 完整 10 米地表温度生产 | 研究区、时间、产品方式 | 完整 7 步主链 |
| `gapfill` | 对已有主图填洞 | 研究区 | 独立填洞（不覆盖主图） |

必需字段表在 [core/agent/understanding/capabilities.py](../core/agent/understanding/capabilities.py)。`create` 必须带 `capability`；缺失或取值不在表内，整条候选判无效。

## 5. 允许的槽位字段（`patches` 的键）

| 字段 | 值怎么写 | 程序随后做什么 |
|---|---|---|
| `region` | 用户原话里的地名，如「武汉」；**禁止写文件路径** | 在真实研究区目录里先收全部候选再判唯一，绑定路径与内容指纹 |
| `time` | 用户原话里的时间表达，如「7 月」「去年七月」「2025-07-15」；**原样抄，不要自己换算** | 以消息接收时间 + 用户时区为锚点解析成绝对起止；单日不扩成整月；模糊时间先追问 |
| `product_mode` | 只能是 `pair` / `monthly` | 完整生产且时间是整月时才需要，缺失就追问；非整月按配对，来源记为默认 |
| `datasets` | 数组，只能取 `landsat` / `sentinel2` / `dem` | 表外取值一律剔除 |
| `product` | 只能是 `lst_10m` | 缺失时补默认，来源记为默认 |
| `model` | 只能是 `rf` | 同上 |

### 5.1 补丁动作（`action`）

| 取值 | 含义 |
|---|---|
| `set` | 本轮明确给了这个值 |
| `clear` | 本轮否定了这个值（`value` 写被否定的内容） |
| `keep` | 本轮没提到，保持原样（等价于不写这条补丁） |

`set` 却不给 `value`，这条补丁判无效。

### 5.2 `evidence` 为什么重要

`evidence` 是这条补丁在用户原句里的依据片段。它不只是给人看的：

程序用它判断「这个值是不是用户**本轮**真的说了」。模型经常把上文里的旧值一并回显，如果一个值曾被否定过（用户说过「不是武汉」），只有在本轮原句里能找到对应的字，才允许它撤销那条否定记录。判据实现见 `slotbook.grounded_in_message()`。没有这一道闸，「不是武汉」之后模型回显一次武汉，历史合槽就把它填回来了——这正是升级方案 9.2 第 4 条要修的毛病。

## 6. 共享修饰（`shared_modifiers`）

用于「武汉 7 月、南京 8 月，**都是 2025 年**」这类一句话里的公共信息。

| 字段 | 说明 |
|---|---|
| `patches` | 与操作里的字段补丁同构 |
| `applies_to` | 作用于哪几个临时标签。**必须显式写出** |
| `evidence` | 原句依据 |

规则：

- `applies_to` 缺失 → **整条丢弃**并记一条警告，程序不替模型做笛卡尔积；结果是少合并一次、多问一句，而不是凭空造出用户没要的任务。
- 目标本轮没给该字段 → 直接采用共享值。
- 目标本轮给了该字段：**时间是互补关系**（共享年 + 各自月），拼成一句交给确定性解析（「2025 年」+「7 月」→「2025 年 7 月」）；其余字段按槽位优先级由目标自己的值胜出。
- 标签不在 `applies_to` 里的目标完全不受影响。

## 7. 其余字段

| 字段 | 说明 |
|---|---|
| `label` | 只在本条消息内用于绑定的临时标签（A / B）。**正式任务编号由后端生成**，模型不能指定 |
| `target_ref` | 原句里的指称：「南京」「第二个」「这张图」。程序按「明确编号 → 序号 → 地区/标签 → 唯一未完成任务」的顺序绑定，多个合理目标一律追问 |
| `question_id` | `op=answer` 时指向的待答问题编号（从上下文里给出的待答问题列表中取） |
| `answer_text` | `op=answer` 时的答复原文 |
| `missing` | 模型认为还缺的字段。**只作提示**，程序按能力表自己判 |
| `ambiguity` | 模型察觉到的歧义，记入任务的歧义字段 |
| `note` | 一句话说明理解结果，只进日志不进气泡 |

## 8. 模型禁止做的事

1. 输出可执行计划、步骤列表、技能名、Python 代码或任何文件路径。
2. 编造用户没说的信息（补年份、补月份、替用户选产品方式）。
3. 把一个日期扩成整月，或把「最近」「夏天」换算成具体月份。
4. 把被否定的内容当成新信息（应该给 `clear`，不是 `set`）。
5. 省略 `shared_modifiers.applies_to`。
6. 输出枚举表以外的操作类型、能力或字段名。

## 9. 校验与失败处理

| 情况 | 程序行为 |
|---|---|
| JSON 解析失败 / 枚举外内容 | 用更严格的提示**修复一次**；仍无效则如实说明「没能整理成可执行的操作」，保留已确认信息 |
| 模型超时或不可用 | 如实说明「暂时联系不上语言模型」，保留已确认信息 |
| 无效输出 / 模型不可用 | **一律不建任务、不产生追问**；不用默认城市、整月、下载或全流程兜底 |
| 共享修饰缺作用范围 | 丢弃该条并记警告，其余候选照常使用 |
| 候选数量超上限 | 整批判无效 |

「致命错误」（枚举外内容）会让整批候选作废；「警告」（已安全丢弃的部分）不影响其余候选——这条区分在 `CandidateBatch.errors` / `CandidateBatch.warnings` 里。

## 10. 一条消息走完全程的样子

以「武汉 7 月、南京 8 月，都是 2025 年，月度产品」为例（真实经 HTTP 返回的模型输出见 [理解层_阶段2交付报告.md](理解层_阶段2交付报告.md) 附录 A）：

1. 模型返回两条 `create` + 一条 `applies_to: ["A","B"]` 的共享年份修饰。
2. 程序合并共享修饰：A 的时间变成「2025 年 7 月」，B 变成「2025 年 8 月」。
3. 程序把「武汉」「南京」分别绑定到真实边界文件，各自记内容指纹。
4. 程序以消息接收日期为锚解析时间，得到两段绝对区间。
5. 两条能力必需信息齐全 → 登记成两个独立任务，各自一次「草稿修改」事务，状态 `ready`。
6. 不产生任何追问；第一个任务交执行链，第二个排队等待（调度器是阶段 4 的事）。
