## 一、先打个比方：现在的系统像什么

### 现在的系统 = 一位"只能一心一用的学徒"

你跟他说："帮我做武汉和南京的温度图。"

他会犯这些错：

- **记性差**：他脑子里只有一块小黑板（一套槽位），写不下两个城市的需求。你说了武汉 7 月、南京 8 月，他可能记成"某个地方 8 月"。
- **一根筋**：他一旦开始干活，就埋头做到底。你中途喊"南京那个先停一下""武汉的数据换成 6 月"，他听不见——因为他正忙着算数，而且没有小本本记录你说过什么。
- **靠猜**：你说"继续"，他看一眼桌上最近的一张图，猜你是想"给这张图补洞"。你说"不是武汉"，他擦掉武汉，但一会儿又凭着老习惯把武汉写了回去。
- **睡一觉全忘**：他（程序）一旦打盹（服务重启），小黑板被擦光，正在干的活全部作废，你只能从头再来。
- **不顾家底**：家里就一口锅（一台服务器的内存），他却想把所有菜同时下锅。下载一张 2GB 的卫星图，他会先把整张图捧在手里（整文件缓存在内存里），手都要撑爆了。

### 升级后的系统 = 一位"带团队、有台账的项目经理"

- **有台账**：每个需求都登记成一个正式"任务"，有编号、有版本、有状态，写进数据库。说过的每句话都留痕。
- **会拆活**：你说"武汉 7 月、南京 8 月"，他登记成两个独立任务，各自推进，互不干扰。
- **随叫随到**：任务在跑，你随时可以说"南京停一下""武汉改 6 月"，他翻台账就能找到对应任务处理，不用打断手头所有事。
- **忘不掉**：所有状态都在数据库里。服务重启后，他翻翻台账，从上次的进度接着干。
- **会管资源**：家里一口锅，他就排队用；家里四口锅，他就并行炒。下载大文件改成"边下边写到硬盘"，不再捧在手里。

## 二、现在的系统有哪些具体的毛病

以下是代码里真实存在的问题（我已逐一核对过代码，不是猜测）：

### 毛病 1：只记得"一套"信息

现在的槽位系统（`core/agent/roles/slots.py`）一个对话只有一套信息：一个地区、一段时间、一种产品方式。这是所有"不智能"感觉的根源。

### 毛病 2：任务在跑，系统就"聋"了

`server.py` 的 `chat_start()` 给每个对话开一条后台线程，线程跑完之前，同一条对话再来消息会被拒绝。你想中途改需求、加任务、问进度，都做不到。

### 毛病 3：关键词会"劫持"你的意图

系统里有一层关键词硬规则，优先级高于模型的理解。比如你说"继续"，规则看到项目里有现成的温度图，就强行把"继续"解释成"补洞"——哪怕你想表达的是别的意思。

### 毛病 4：等待用户靠"阻塞线程"

审批、追问靠 `threading.Event` 让线程原地睡觉等答案。这个等待只存在于内存里：服务一重启，等待就没了，任务卡死在半路。

### 毛病 5：找结果靠"最新的文件"

地图、精度、下载入口都是去找目录里"最新的那个文件"。没有正式的"这件结果是谁、哪次运行、什么参数生产的"的登记。两个任务同名输出就可能串了。

### 毛病 6：没有资源管理

- 下载会把整个文件读进内存再写盘（`_fetch_asset` 累积字节块再拼接）。
- 没有全局预算：多个任务同时来，会互相抢内存，最坏把服务挤崩。
- 没有排队和调度概念，全靠"谁先来谁先跑完"。

### 毛病 7：否定和默认值出问题

你说"不是武汉"，这个否定没有被持久记录，历史信息又把武汉合并了回来。反过来，系统默认值有时被记成"用户亲口说的"。

## 三、升级之后是什么样子

用一段用户视角的"剧本"来描述。假设升级完成，你说：

> "做武汉和南京 2025 年 7 月的 10 米地表温度，都按月合成，先出武汉。"

系统会发生什么（你能看到的）：

| 时刻               | 你看到什么                                                                                                 |
| ------------------ | ---------------------------------------------------------------------------------------------------------- |
| 消息发出后 1 秒内  | 消息显示"已接收"，立刻出现**两张任务卡**：任务A（武汉）、任务B（南京），卡上写着地区、月份、产品方式 |
| 接着               | 系统从数据库匹配到两个城市的边界，没有缺项，不追问，直接开始                                               |
| 几分钟后           | 武汉开始下载数据；下完武汉的，南京的下载自动开始（**和武汉的计算同时进行**）                         |
| 武汉算完           | **武汉的地图、精度、下载入口立即可用**——不用等南京，不用等报告写完                                 |
| 此时你看任务卡     | 武汉显示"已完成"，南京显示"计算中"，评价和报告在后台继续                                                   |
| 中途任何时候       | 你可以说"南京改成 8 月"——只有南京的任务更新版本重新排队，武汉完全不受影响                                |
| 你关掉浏览器再打开 | 所有任务卡状态原样恢复，什么都没丢                                                                         |

一句话总结升级目标：**一句话可以变多个任务、任务可中途修改取消、第一份结果先出先看、断线重启都不丢。**

## 四、升级的五大核心改动

原文档 1000 多行，其实核心就是五件事。按重要性排序：

### 改动 1：给系统装一个"任务台账"（数据库）

**改什么**：新建一个 SQLite 数据库（就是一个小型单文件数据库，Python 自带，不用装新软件），登记这些信息：

```
任务（用户想做的一件事）
 └── 运行（这个任务某一次实际执行，改需求会产生新运行，旧的留档）
      └── 节点（可独立完成和恢复的一小步：下载、预处理、训练……）
           └── 尝试（某节点的一次执行，失败重试就是新尝试）
                └── 产物（这步成功后产出的正式文件）
```

同时还登记：对话消息、待回答的问题、关键事件（给前端推送用）。

**为什么重要**：这是地基。后面所有能力——多任务、中途修改、断点恢复、结果不串——都依赖"每件事都有编号和记录"。现在的系统没有台账，所以什么都做不到。

### 改动 2：模型只"提建议"，程序做决定

**改什么**：现在的流程是"模型理解 → 生成完整计划 → 直接执行"。改成：

```
模型输出：    "用户似乎想新建一个 LST 任务，地区可能是武汉，时间是 7 月"
                ↓ （只是候选建议）
程序校验：    武汉这个边界真实存在吗？7 月缺年份吗？和已有任务冲突吗？
                ↓
程序决定：    信息齐全 → 登记任务并开工
              信息缺失 → 生成一条"持久问题"，问用户，答案也走台账
```

**为什么重要**：模型有时会幻觉、会猜。把"理解"和"决定"分开后，模型猜错最多是白猜一次，程序不会放行一个不存在的地区或编造的步骤。同时"追问"从内存等待变成台账记录，重启也不丢。

### 改动 3：计划变成"节点图"，加一个统一调度器

> 思想来源说明："节点图 + 状态持久化 + 暂停/恢复"借鉴了 LangGraph 的设计思想，"唯一调度器 + 按资源派发"借鉴了经典工作流引擎的概念。但**只借思想、不装框架**——用现有 Python + SQLite 自己实现，原因见第七节 Q1。

**改什么**：现在是一个执行器按顺序调 7 个技能（`WORKFLOW_STEPS`），一条道跑到黑。改成：

1. 确认后的任务被"编译"成一张依赖图（先搜索 → 再下载 → 再预处理 → ……）
2. 一个唯一的**调度器**盯着这张图：哪个节点的依赖满足了、资源够用，就派给执行进程去跑
3. 下载和计算是不同类型的节点，可以**交错**：A 城市在计算时，B 城市可以同时下载

**为什么重要**：这是"多任务不排队、资源不打架、单节点失败只重跑这一步"的基础。也是"先出武汉结果"能实现的原因。

### 改动 4：产物"两步提交"，杜绝半成品

**改什么**：现在节点算完直接把文件写进正式目录。改成：

```
第一步：节点把结果写进自己的"暂存目录"（每次尝试一个独立目录）
第二步：程序验证文件完整、正确后，才"发布"为正式产物，登记进台账
```

**为什么重要**：杜绝三类经典事故——①半成品被下游当成完整输入用；②旧的重试覆盖了新结果；③文件写了一半服务崩了，留下一个损坏文件被当成正式结果。同时每份产物记录"我来自哪次运行、用什么输入、什么参数"，地图/精度/下载都按编号找它，不再按"最新的文件"猜。

### 改动 5：前端改成"任务卡 + 事件流"

**改什么**：现在前端基本是"一条聊天流 + 一个执行状态"。改成：

- 一个对话里多张**任务卡**，各自显示自己的状态、进度、等待原因
- 问题以**卡片**形式呈现，绑定具体任务和版本，过期卡片点了会提示"已失效"而不是错误执行
- 前端断线重连时，靠"事件序号 + 状态快照"补齐错过的更新，不用刷新重来

**为什么重要**：前面四条改动的价值，最终都要通过界面让用户感知到。

## 五、分几步做、每步做完你能看到什么

文档建议按依赖顺序分 7 步（原文叫"工作包"）。**注意：这些步骤是层层依赖的，不能跳着做。**

> 关于"回归用例"：不再单设一个"跑基线"阶段。项目此前已有跑通的正常结果，只需从中挑一个成功案例，把输入、参数、随机种子、软件环境记录在案（轻量工作）。此后每批改完，用同样输入复跑对比，确认算法结果一致——这是"保证不破坏原始算法"的唯一可靠手段。

| 阶段                    | 做什么（人话版）                                                                     | 做完后你能看到什么                                                                     | 对应原文档 |
| ----------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- | ---------- |
| **1. 状态内核**   | 建 SQLite 台账 + 命令接收服务（去重、版本校验）；顺手登记一个历史成功案例作为回归用例 | 系统有了"记账"能力，但用户界面还没变                                                   | §3、§15.5 |
| **2. 理解层**     | 模型改输出"候选操作"，程序做绑定/校验/追问                                           | **能分清"武汉 7 月、南京 8 月"了；说"不是武汉"不会回来了；重启不丢等待中的问题** | §4        |
| **3. 计划编译**   | 确认的任务编译成节点图；参数在开工前"拍照冻结"                                       | 排队时改设置界面，不影响已提交的任务                                                   | §5        |
| **4. 调度与执行** | 节点用独立子进程跑；下载改流式；加资源账本                                           | 武汉计算、南京下载同时进行；内存不再爆；失败只重跑单节点                               | §6–9     |
| **5. 产物与恢复** | 两步提交、引用保护、重启对账                                                         | 半成品不再混入；服务重启后从断点继续                                                   | §10–11   |
| **6. 界面**       | 任务卡、问题卡、事件流、断线恢复                                                     | 你在界面上直观看到多任务各自推进                                                       | §12       |
| **7. 记忆与部署** | 实验记录可靠写回；Docker 数据目录持久化                                              | 容器重建后账号、边界、任务、结果都在                                                   | §13       |

### 我的实施建议

- **第一批做 1 + 2**：这是"智能感"提升最明显的部分（多目标、可修改、不丢状态），而且风险相对可控。
- **第二批做 3 + 4**：这是性能和可靠性部分，工程量最大，但做完才有"交错执行"。
- **第三批做 5 + 6 + 7**：收尾保障。
- 每一批结束时系统都应该**仍然可用**（旧功能不坏），而不是改到一半系统瘫痪。
- 每个阶段的工作内容与验收操作见[第九节](#九每个阶段做什么怎么验收给你和合作者)——把某个阶段交给谁开发，就把对应小节整段发给他。

## 六、绝对不能动的东西

原文档反复强调：这次升级**只改编排层（大脑和管家），不改科学算法（手艺）**。以下内容一个数值都不能变：

| 必须原样保留                               | 说明                             |
| ------------------------------------------ | -------------------------------- |
| 数据定标、QA/SCL 掩膜规则                  | 卫星数据怎么变成温度的换算规则   |
| 配对模式（时间差 ≤ 2 天）与月度中位数合成 | 两种产品方式的科学定义           |
| 空间块划分 + 缓冲区的训练/验证/测试切分    | 不能换随机种子、不能重新划分     |
| TTRI 只用固定训练集拟合一次                | 不能每轮调参都重新拟合           |
| RF 调优规则与选优口径                      | 线程数可以分配，科学超参数不能动 |
| TCR 按真实 30 米父格回加残差               | 校正的数学不变                   |
| 主产品和填洞产品分开                       | 填洞不覆盖主图                   |

**为什么**：调度系统再好，如果它悄悄改变了降尺度结果，这个系统就失去意义了。所以那张登记过的"历史成功案例"（见第五节开头的说明）是所有改动的安全网——每批改完都要用同样的输入复跑，对比结果一致才放行。

## 七、常见疑问

**Q1：要不要换成 LangChain / LangGraph / AutoGen 这类 Agent 框架？**
不换。文档明确拍了板：框架解决不了我们的核心问题（缓存身份混乱、下载占内存、线程阻塞等待），迁移框架反而会引入新风险。借鉴它们的思想（状态持久化、暂停恢复），但用现有 Python 自己实现。

**Q2：为什么要用 SQLite？不用更高级的数据库？**
一台服务器、有限并发，SQLite 完全够用，而且它是 Python 内置的，零部署成本。文档明确说不用 Redis、不用 Celery、不用分布式队列。

**Q3：升级后还需要四个"角色"Agent 吗？**
需要。Planner（理解）、Data（选数据/查质量）、Train（调参）、Eval（评价）都保留，只是它们的建议都先入台账、由程序核验后执行，不能再"自己开线程干活"。

**Q4：这个升级工作量有多大？**
很大。相当于把后端的"指挥系统"重写一遍，前端大改。文档也明确说了：不能只加提示词、加个任务卡、或者在外面套个线程池就算完事。分三批做，每批都有可感知的成果。

**Q5：改完之后，老对话和老结果还在吗？**
在。老对话保留原文，老结果核验后登记为"历史产物"。缺信息的地方如实标"未知"，不会伪造"曾经成功"的记录。

**Q6：用户需要配置很多参数吗？**
不需要。默认就是"1 个计算作业 + 1 个下载作业交错"，开箱即用。服务器好的管理员可以调大并发，程序会自动按总预算分配。

## 八、名词小词典

遇到原文档里的黑话，查这张表：

| 名词             | 人话解释                                                   |
| ---------------- | ---------------------------------------------------------- |
| 槽位             | 一个任务需要填的空：地区、时间、产品方式等                 |
| 任务（task）     | 用户想做的一件事，有编号有版本，记在台账里                 |
| 运行（run）      | 任务某一次实际执行。改了需求就产生新运行，旧运行留档       |
| 节点（node）     | 可以独立完成、独立重跑的一小步工作                         |
| 尝试（attempt）  | 某节点的一次执行。失败了重试，就是新尝试                   |
| 产物（artifact） | 一步成功后产出的正式文件，登记了"来自哪次运行、用什么输入" |
| 快照             | 开工前给所有参数"拍的照片"，之后改设置不影响它             |
| 调度器           | 唯一的"管家"，决定哪个节点什么时候、用多少资源去跑         |
| 资源账本         | 记录 CPU、内存、磁盘、下载连接各被谁占了多少的本子         |
| 两步提交         | 先写暂存区 → 验证通过 → 才发布为正式文件                 |
| 引用保护         | "这个文件还有下游要用，谁都不许删"的标记                   |
| 血缘             | 一个文件"从哪来"的完整记录（哪次运行、什么输入、什么参数） |
| 幂等             | 同一个请求重复发，只生效一次（防止双击导致重复执行）       |
| 事件流（SSE）    | 服务器往前端持续推送状态更新的长连接                       |
| 持久问题         | 存进台账的"待用户回答的问题"，重启也不丢                   |
| spawn            | 启动全新干净子进程的方式，避免子进程继承一堆不该有的东西   |
| COG              | 云优化 GeoTIFF，支持"只读文件的一小块"而不下载整景影像     |
| 交错执行         | A 在计算的同时 B 在下载，锅和灶同时都在用                  |

## 九、每个阶段做什么、怎么验收（给你和合作者）

开发可能分散给多位合作者，所以每个阶段包含三部分：**要做什么**（工作内容，可直接发给开发者）、**你怎么验收**（你亲手做的检查）、**合作者必须交付的物**。第五节的表格只是总览；把某个阶段交出去时，把本节对应小节整段发给他即可。

### 9.0 三条铁律（每个阶段都适用）

1. **回归红线**：每个阶段验收前，开发者必须用 [回归用例_武汉20240722.md](回归用例_武汉20240722.md) 的输入冻结复算跑一遍，附上数值对比表。对不上就不验收，且**不允许放宽容差直到通过**。
2. **旧功能不坏**：升级前能做的事（单城市完整生产、Chat 问答、上传边界、查看历史结果），验收时抽查一遍必须照常工作。
3. **交付不齐不验收**：没有下方"交付物清单"里的东西，视为阶段未完成。

### 9.1 阶段 1：状态内核

**这一阶段要做什么：**

1. 建 SQLite 数据库和表：任务、运行、节点、尝试、产物、问题、事件、消息等（每张表存什么、字段含义按总体技术方案 §3.2 的表执行）。
2. 命令接收服务：用户消息先持久化再处理；同一请求编号+相同载荷只生效一次（去重）；接收后立刻返回回执，不等任务完成。
3. 单一写入者：全系统只有一个控制线程写任务库，用短事务（`BEGIN IMMEDIATE`），任何错误显式回滚，不吞异常。
4. 对象版本号：任务/问题/运行每次修改递增版本，旧版本的操作请求会被拒绝（防止迟到结果覆盖新状态）。
5. 事件记录：关键变化（命令接收、状态变化等）写入事件表并带递增序号（前端后面靠它同步）。
6. 数据库结构版本号 + 迁移脚本：以后改表结构要走带备份的迁移，不直接改。
7. 顺手把回归用例登记成文（已完成，见回归用例文档）。

**这一阶段不做什么**：不改理解层和执行器（那是阶段 2、4 的事）；不改界面；不改任何科学算法。

**你怎么验收：**

1. 让开发者启动服务，随后**重启一次服务**，然后检查：之前登记的任务/消息记录还在不在（开发者应提供一条查看台账的命令或界面入口）。
2. 让开发者演示"同一请求发两次"：台账里只应记一次（命令去重生效）。
3. 看交付物里有没有建表脚本和字段说明。

**通过标准：** 数据库文件真实存在且随服务持久化；重启不丢数据；重复请求只记一次。

**合作者必须交付：** 代码；SQLite 建表脚本/迁移；一页表结构说明（每张表是干什么的）；回归用例复跑记录。

### 9.2 阶段 2：理解层

**这一阶段要做什么：**

1. 把现在的 Planner 拆成"候选理解器"：模型只输出受限的候选操作（新建/设值/清除/更正/回答/继续/重试/取消/只回答），加字段补丁和原句依据，不再直接生成可执行计划（总体技术方案 §4.1）。
2. 目标绑定：候选里的"武汉""第二个""这张图"绑定到真实边界文件或台账中的任务；绑不唯一就追问，不猜。
3. 时间解析：复用现有 `parse_time_expression`，但以消息接收时间为锚，存绝对起止日期和原表达；单日不扩成整月，模糊时间先问。
4. 否定与清除："不是武汉"真正清空地区并留下否定记录，历史不会把值填回来；系统默认值不得记成"用户亲口说"（每个槽位存值+来源+是否确认）。
5. 持久问题：追问存进台账（含候选列表和目标版本），答案一次消费；文字回答和卡片点击走同一处理入口。
6. 等待不再阻塞线程：现在靠 `threading.Event` 睡觉等答案的逻辑，改成返回"需要输入"后释放资源，答案到了再继续。
7. 失败兜底：模型超时或输出无效时保留已确认信息、明确说明，不用默认城市/下载兜底；Chat 模式禁止创建生产任务。

**这一阶段不做什么**：不编译节点图（阶段 3）；不实现调度；不改 Skill 内部逻辑。

**你怎么验收（照着对话测，全部在 Work 模式）：**

| 你说 | 必须看到 |
|---|---|
| "武汉 7 月、南京 8 月，都是 2025 年，月度产品" | 两个任务，各自绑定正确月份，**不串** |
| "不是武汉"（随后接着说别的） | 武汉被清除，后续不出现武汉下载 |
| "武汉去年 7 月做 LST"（不提年份上下文时） | 追问年份或用明确的锚点日期，**不拿当前年冒充** |
| "只下载 Sentinel-2" | 只下载，不自动开始训练 |
| Chat 模式问"什么是地表温度" | 只回答，不建任何任务 |

**重启加分项**：追问出现后重启服务，问题还在；回答后任务继续。

**通过标准：** 上表 5 条全部符合；追问只问真正缺的信息。

**合作者必须交付：** 代码；"候选操作"格式说明（模型允许输出哪几种操作）；覆盖上述 5 条场景的测试记录（附模型原始输出）。

### 9.3 阶段 3：计划编译

**这一阶段要做什么：**

1. 能力目录：给每种用户目标（搜索/下载子集/局部处理/完整 LST/填洞/查询）写清楚允许的目标、必需字段、允许参数、输入输出（总体技术方案 §5.1）。
2. 编译器：确认后的任务草稿编译成节点图——节点、依赖边、完整生产主链模板；未知步骤返回校验失败，不能悄悄删掉后说计划有效。
3. 参数快照冻结：进入队列前把所有参数"拍照"存档，并逐项记录来源（快照/用户/默认）；排队和执行中改设置界面都不影响它。
4. 缺输入时显式插入重建节点：不再允许 Skill 内部顺手重跑上游；重建也要走申请和授权。
5. 修改与重规划规则：改日期/边界/产品方式 = 新任务版本+新运行，旧运行留档；重规划次数和调优额度持久记录，重启不归零（§5.4）。

**这一阶段不做什么**：不真正派发执行（阶段 4）；不改 7 步主链的定义本身。

**你怎么验收：**

1. 提交一个任务，让它排队；排队期间去设置界面改参数（云量、模型参数等），再查该任务的"冻结参数快照"（开发者应提供查看入口）——**必须还是提交时的值**。
2. 看任务详情：能看到它被拆成了哪些节点、依赖顺序对不对（先下载后预处理）。

**通过标准：** 排队中改设置不影响已提交任务；每个任务可查参数快照和节点清单。

**合作者必须交付：** 代码；节点图与能力模板说明；快照查看方式说明；回归记录。

### 9.4 阶段 4：调度与执行

**这一阶段要做什么：**

1. 唯一调度器控制循环：事件唤醒（空闲最长 1 秒检查一次），找依赖满足的节点，按"用户优先级 > 主产品推进 > 保护队列防饿"的顺序派发（§8.5）。
2. 资源账本与生效配置：启动时检测容器 CPU/内存限制，生成预算；派发前估算节点峰值并预留，实测超限就停止新派发（§9）。
3. 节点工作进程：每个节点用 `spawn` 起独立子进程，先设置资源额度再导入算法库，跑完退出；取消、超时、崩溃都有统一收尾（§8.3）。
4. 下载改造：分块流式写入暂存文件（不再整文件缓存在内存）；限全局连接数；分片校验与续传；同一缓存项只允许一个获取者（§7.2–7.3）。
5. 数据获取拆步：检索/选择/取数/本地准备分开，各自成为独立节点；配对选择结果固化为不可变选择记录（§7.1）。
6. 执行额度参数：`n_jobs` 这类线程数由调度器作为"额度"传入，与科学超参数白名单分开；GDAL/BLAS 线程也限制在同一额度内（§6.3）。
7. 授权与旧进程对账：每次尝试有唯一提交授权；服务重启时核对旧进程身份，不重复启动也不误杀无关进程（§8.4）。

**这一阶段不做什么**：不实现两步提交（阶段 5，本阶段产物先写暂存）；不改任何算法内部实现。

**你怎么验收：**

1. 发"武汉和南京都做"：观察两张任务卡——武汉在"计算"时，南京应能同时"下载"（卡状态同时变化，不排队等）。
2. 下载大文件时看资源面板/任务管理器：内存不应随文件大小（如 2 GB）同步飙升。
3. 让开发者演示人为制造一次节点失败（如临时断网）：只有该节点重试，**其他任务不受影响**，且失败原因在界面可见。

**通过标准：** 交错执行真实发生；下载内存有界；单点失败不扩散。

**合作者必须交付：** 代码；资源预算默认值表（几路下载、几路计算、内存磁盘怎么算）；模拟失败的演示记录；回归记录。

### 9.5 阶段 5：产物与恢复

**这一阶段要做什么：**

1. 目录规范：运行目录、每次尝试的私有暂存目录、提交后的不可变发布目录；输入区与输出区分开（§10.1）。
2. 两步提交：暂存完成描述 → 核对授权与版本 → 文件发布到唯一目录 → 数据库原子登记产物/节点成功/事件；文件和数据库不是原子事务，靠对账补齐（§10.2）。
3. 产物登记：每份产物记录类型、位置、完整性、来自哪次运行、什么输入（血缘）；"已按政策清理"和"意外丢失"区分开（§10.3）。
4. 引用保护：持久依赖（下游/模型/续接要用）和活动使用（正在读/下载）分开登记；清理前必须两者都无（§10.4）。
5. 启动对账：服务重启时按提交中断点处理表逐项对账（§11.2），该续的续、该撤销的撤销，不重复计算也不伪造成功。
6. 受控清理：登记待删 → 确认无引用 → 删除 → 更新状态；正式结果和用户数据默认永不自动删（§11.4）。

**这一阶段不做什么**：不改调度顺序；不改算法输出格式。

**你怎么验收：**

1. 让一个任务跑到一半（如训练中）**重启服务**：恢复后从已完成的节点继续，不从头重算，且之前的结果还在。
2. 查任意一个正式结果：有编号，能查到"来自哪次运行、什么输入"（产物身份信息）。
3. 让开发者演示"计算中途杀掉进程"：不应产生任何正式结果文件，界面如实显示失败。

**通过标准：** 断点续跑正确；产物可溯源；半成品永远不会变成正式结果。

**合作者必须交付：** 代码；两步提交与恢复逻辑说明；各宕机点的恢复测试记录；回归记录。

### 9.6 阶段 6：界面

**这一阶段要做什么：**

1. 新接口：会话快照、任务详情、回答问题、任务命令（取消/重试/优先级）、事件流、产物查询下载（§12.1 的建议契约）。
2. 事件与断线补发：关键状态落库；重连时"快照 + 按序号补发"，前端按版本号拒绝旧状态覆盖新状态（§12.2）。
3. 前端状态重构：任务卡按任务编号、问题卡按问题编号存状态（现在 `chat.js` 的 paused/approval 只代表一条执行链）；一条事件连接服务整个对话的多任务（§12.3）。
4. 结果绑定产物：地图、精度、下载统一按产物编号取，不各自找"最新文件"。

**这一阶段不做什么**：不改后端状态逻辑；不重做登录系统。

**你怎么验收（纯浏览器操作）：**

1. 发多城市消息 → 多张任务卡各自推进、各自显示状态和等待原因。
2. 武汉完成后**立即**能看地图/下载，不等南京、不等报告。
3. 浏览器断网 30 秒再恢复：状态自动补齐，不出现重复卡或丢失卡。
4. 一张过期的问题卡点提交：提示"已失效"，而不是错误执行。

**通过标准：** 上述 4 条全过；切换历史结果时地图、精度、下载指向同一份产物。

**合作者必须交付：** 前端构建产物；关键界面的截图或录屏；回归记录。

### 9.7 阶段 7：记忆与部署

**这一阶段要做什么：**

1. 记忆写回待办：任务成功事务中登记写回待办，单独执行器调用实验记录/成功流程/向量库适配器；失败有限重试，不阻塞结果展示（§13.2）。
2. 记忆与运行状态分离：记忆只提供建议，不决定任务是否完成；现有 workflow_experience 的入库门槛（含测试 R²≥0.75）保留（§13.1）。
3. 主服务内存收束：用户 Agent/记忆对象按容量淘汰，嵌入模型共享只读实例，搜索缓存加容量限制和过期清除（§13.3）。
4. Docker 持久化：统一数据根（默认 `/app/data`），接通现有各模块的硬编码路径；SQLite 必须在本地持久盘，不随项目盘搬到网络目录（§13.4）。
5. 预算配置校验：作业数/连接/CPU/内存/缓存等配置项带中文说明，无效配置拒绝启动，不悄悄采用无限值。
6. 旧数据兼容：老对话保留原文和编号映射；老结果核验后登记为历史产物，缺证据的标未知，不伪造记录（§13.5）。

**这一阶段不做什么**：不改调度和算法；不新增外部服务（Redis/Celery 等）。

**你怎么验收：**

1. 跑完一个任务后查实验记录：参数、指标、结果真实入库（不是空壳）。
2. **容器重建演练**：删掉容器（保留数据卷）重新启动——账号、边界、任务、结果全部还在。

**通过标准：** 记忆写回可靠（失败会重试且不阻塞结果展示）；容器重建后一切可找回。

**合作者必须交付：** 代码；部署配置说明（数据根、预算参数怎么配）；容器重建演练记录；回归记录。

### 9.8 交给合作者开发时的通用流程

1. **开工前**：把本节对应阶段的验收标准和原文档对应章节发给开发者，明确"按这两个文档实现，不重新讨论已拍板的决定"。
2. **开发中**：每个阶段是独立的验收单元，做完一个验一个；不要攒到最后一起验。
3. **交验收**：开发者按"交付物清单"提交，你按验收操作逐条执行；回归对比表是第一道关。
4. **不通过时**：退回并附上你观察到的现象（哪条操作、看到什么、期望什么）；修完后**重新跑全条验收**，不是只验修改处。
5. **接缝责任**：阶段之间有依赖（2 依赖 1、4 依赖 3、6 依赖 1），接缝处的接口由上游阶段负责先交付契约文档，下游据此开发——避免两人各写各的接不上。
