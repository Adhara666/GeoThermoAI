# 回归复跑记录：升级第二阶段（理解层）验收

复跑日期：2026-09-09 / 09-10。依据 [回归用例_武汉20240722.md](回归用例_武汉20240722.md) §7。

**结论先说**：科学算法**没有**被第二阶段改动破坏。判据是「同一份原始输入，旧代码与新代码逐位一致」——32 项对比 0 项不同，连 `train.parquet` / `test.parquet` 的 SHA-256 都完全相同。

与登记基线之间存在**小幅偏差**，原因经 provenance 核对确认是**远程数据源的输入本身变了**（Sentinel-2 场景集合从 2 景变成 4 景），不是编排层问题。这正是回归用例 §7 对「完整复跑（含下载）」预先标注的风险，处置方式也按该节要求执行：先核对场景编号，再判断责任归属。

## 1. 这次跑了什么

用户要求「调用现在程序的算法走全流程包括下数据」，因此这次做的是回归用例 §7 的**第 2 级完整复跑**，而不是第一阶段那种输入冻结复算（第一阶段用的 Docker 卷 `geothermoai_data` 不在本机，冻结输入已不可得）。

| 项 | 值 |
|---|---|
| 镜像 | `geothermoai-image:latest`（由本仓库 Dockerfile 现场构建，GDAL 3.9.3 / Python 3.12） |
| 资源限额 | `--memory=16g --cpus=16` |
| 研究区 | 仓库根目录 `武汉市_市.geojson` |
| 检索窗口 / 云量 | 2024-07-01 ~ 2024-07-31，云量上限 30% |
| 驱动脚本 | [tests/regression_wuhan20240722.py](../tests/regression_wuhan20240722.py) `--download` |
| 输出目录 | 卷内 `/app/data/regression_stage2/`（独立目录，不覆盖任何历史结果） |

走的是**生产路径本身**，不是另写一份下载代码：检索与下载调用 `DataAcquisitionSkill`，主链调用 `EasyLSTPipeline`。所以「下载环节有没有被编排层改动破坏」也在这次回归的覆盖范围内。

全流程实际跑完的环节：STAC 检索 → 配对构建 → 选定登记配对 → 下载 Landsat LST/QA + Sentinel-2 五波段/SCL + DEM → 预处理与空间划分 → TTRI 一次拟合 → RF 训练与测试预测 → TCR → 导出 GeoTIFF → 粗尺度闭合评价。

## 2. 场景身份核对（§7 要求的第一步）

检索结果里**包含**登记用例那对影像，程序按登记配对下载：

| 项 | 登记值（2026-08-14） | 本次（2026-09-09） | 一致？ |
|---|---|---|---|
| Landsat 日期 | 2024-07-21 | 2024-07-21 | 是 |
| Sentinel-2 日期 | 2024-07-22 | 2024-07-22 | 是 |
| Landsat 景 | — | `LC09_L2SP_123038_20240721_02_T1`、`LC09_L2SP_123039_20240721_02_T1` | — |
| **Sentinel-2 景集合** | **T49RGQ、T49RGP（2 景）** | **T49RGQ、T49RGP、T50RKU、T50RKV（4 景）** | **否** |
| S2 处理基线 | N0510 | 05.10 | 是 |
| 定标 offset / quantification | −1000 / 10000（per_scene_xml） | −1000 / 10000（per_scene_xml） | 是 |
| 导出栅格尺寸 | 15 477 × 13 346 | 15 477 行 × 13 346 列 | 是 |

证据：卷内 `regression_stage2/input/sentinel2_provenance_20240722.json`。

武汉横跨 114°E，也就是 UTM 49 带与 50 带的分界。登记那次只用到 49 带的两景，这次目录里多返回了 50 带的 `T50RKU`/`T50RKV`。多出来的两景参与镶嵌后，重叠区里部分像元改由另一景提供，其 SCL 晴空掩膜与原来那景不同，有效像元集合随之小幅变化——这就是下游一连串小偏差的源头。

**这不是编排层能控制的变量**：程序按同样的检索条件问同一个数据源，拿回来的东西变了。

按登记用例的放行标准逐条判：**24 项中 13 项通过、11 项超容差**。超容差的全部集中在「有多少有效像元、这些像元长什么样」这条链上——像元集合变了，TTRI 拟合与极值统计跟着变，这是输入变化的正常传导。

值得注意的是三项**对输入扰动不敏感的整体指标全部通过**：粗尺度闭合（coverage=1.0、MAE 8e-06 K）、最终温度场的均值与标准差（差 0.0007 K / 0.0017 K）。也就是说温度场本身还是同一个场，变的是边缘处哪些像元算有效。极值 min/max 偏移 0.4 K 属于极值统计的正常表现——它只由个别像元决定。

**没有放宽任何容差**：脚本里的容差值与第一阶段完全相同，上表如实标出哪几项没过。

## 4. 决定性证据：同输入下旧代码与新代码逐位一致

既然与登记值的偏差来自输入，那「第二阶段有没有改坏算法」就要换一个能控制变量的方式回答：**同一份刚下载的原始输入，分别用改动前的代码和改动后的代码跑一遍主链，逐项对比。** 这是原文档 §15.5「与原串行路径对照」的同一思路。

| 项 | 值 |
|---|---|
| 对照组 A（旧代码） | 提交 `545c4b6`（第一阶段完成时的树），`git archive` 导出到独立目录后挂进同一镜像 |
| 实验组 B（新代码） | 本次第二阶段工作区 |
| 相同输入 | 卷内 `regression_stage2/input/`（第 2 节那份刚下载的 raw） |
| 对比脚本 | [tests/compare_runs.py](../tests/compare_runs.py) |

结果：**32 项对比，0 项不同。**

| 对比项 | 结果 |
|---|---|
| 划分计数（train/validate/test/buffer_excluded） | 完全一致 |
| 划分方法 / seed / 块大小 / 缓冲 | 完全一致 |
| 5 张中间表行数 | 完全一致 |
| `for_train/train.parquet` SHA-256 | **逐字节相同** |
| `for_train/test.parquet` SHA-256 | **逐字节相同** |
| TTRI 系数 / 截距 / 拟合 R² | 逐位一致 |
| RF test R² / RMSE / MAE / MB | 逐位一致 |
| 最终 LST 栅格尺寸 / 仿射变换 / 投影 / 有效像元数 | 完全一致 |
| 最终 LST min / max / mean / std | 逐位一致 |
| 粗尺度闭合 JSON | 逐字段一致 |

`train.parquet` 逐字节相同这一条尤其说明问题：预处理、掩膜、空间块划分、缓冲区排除的每一个像元决定都没有变。

## 5. 放行判断

| 判据 | 结论 |
|---|---|
| 同输入下旧代码 vs 新代码 | **32/32 一致（含逐字节）** → 算法未被破坏 |
| 与登记基线对比 | 13/24 通过；11 项偏差已定位到输入变化，provenance 有据 |
| 是否放宽过容差 | **否**，容差值与第一阶段完全相同 |
| 全流程可跑通 | **是**，从检索下载到闭合评价 10/10 步骤全部完成 |

**按放行标准放行。** 依据是回归用例 §7 对完整复跑的明确指引：出现差异时先核对 provenance 场景编号，确认是输入本身不同后，再判断是不是编排问题——本次核对结论是输入不同、编排无责，并另有同输入 A/B 的逐位一致作为正面证据。

## 6. 建议（留给后续阶段）

1. **重新登记一份基线**：把这次下载的 raw 输入连同 provenance 冻结保存，作为后续阶段的对照基准；现在这份 2026-08-14 的登记值已经无法用远程数据源复现。
2. **把场景身份纳入快照**：阶段 3 的参数快照应当固化「选定了哪几景」，让同一个运行重跑时不受目录漂移影响（总体方案 §5.3「检索后才知道的场景清单采用一次性绑定」）。
3. MAE 这类对像元集合敏感的指标，容差应当与「输入是否逐位相同」绑定判断，而不是单独设一个绝对阈值。

  --b /app/data/regression_stage2/wuhan20240722
