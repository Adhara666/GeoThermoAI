## 2. 写入方式约定（总体方案 §3.3）

**单一写入者**：全库只有一个写连接，由 `StateStore` 内部的写入者线程（`state-kernel-writer`）独占；任何写入都通过 `submit_write` 排队进入该线程，天然串行。

**短事务**：写事务以 `BEGIN IMMEDIATE` 开始、`COMMIT` 结束；任何异常显式 `ROLLBACK` 后原样抛给调用方，不吞异常。事务内禁止调用模型、下载、计算校验和大文件复制。

**连接参数**：`foreign_keys=ON`、`synchronous=FULL`、`busy_timeout=5000`（写锁等待 5 秒）；默认回滚日志模式，不启用 WAL；台账不放在网络共享目录。

**读路径**：查询走独立读连接 + `BEGIN DEFERRED` 短事务（`StateStore.read`），不在 SSE 生命周期内持有读事务。

## 3. 表清单（对应总体方案 §3.2）

所有业务对象使用后端生成的 UUID 编号（`uuid4().hex`），时间存 UTC（ISO-8601 字符串），用户归属来自鉴权（`server.py` 的 `_uid()`），不接受模型或请求任意指定。

| 表 | 语义 | 关键约束 |
|---|---|---|
| `conversations` | 对话控制状态：旧对话编号映射、语义版本、下一消息序号、对话焦点 | `(user_id, project_id, legacy_conv_id)` 唯一 |
| `messages` | 消息：对话内序号、角色、原文、对应命令、生成状态 | `(conversation_id, seq)` 唯一，外键 → conversations |
| `commands` | 命令：去重键、载荷指纹、操作类型、接收/处理状态、结果 | `(user_id, dedup_key)` 唯一；同键不同载荷报冲突 |
| `tasks` | 任务草稿：目标能力、版本、槽位、汇总状态、优先级、当前运行 | 版本化更新（乐观锁） |
| `runs` | 一次运行：任务及版本、冻结输入、场景绑定、替代运行、取消标记 | 同任务允许多个历史运行 |
| `nodes` | 节点：类型、参数、输入/输出契约、状态、就绪时间、执行顺序 | `(run_id, node_key)` 唯一 |
| `node_edges` | 依赖边：前驱/后继 | `(run_id, predecessor_id, successor_id)` 主键，禁止环由阶段 3 编译器保证 |
| `attempts` | 执行尝试：次数、授权、进程编号、暂存目录、状态、峰值 | `(node_id, attempt_no)` 唯一 |
| `questions` | 问题：类型、候选内容、回答约束、状态 | 版本化更新 |
| `question_targets` | 问题覆盖目标：目标任务/版本/运行/字段 | `(question_id, task_id, field)` 主键 |
| `decisions` | 角色决定：触发节点/轮次、角色、参数补丁、预算消耗 | `(run_id, trigger_node_id, trigger_round, trigger_seq)` 唯一 |
| `artifacts` | 产物：类型、路径、内容标识、输入来源、可用性、保留类别 | `path` 唯一（正式路径唯一） |
| `artifact_refs` | 使用关系：消费者、用途、是否固定使用 | `(artifact_id, consumer_id, usage)` 主键 |
| `commit_intents` | 文件提交意向：输入签名、源/目标目录、输出清单 | `attempt_id` 唯一（每次尝试至多一份意向） |
| `events` | 关键事件：全局递增序号、归属、类型、对象版本、小型载荷 | `seq` 自增主键；不写逐像元/逐 token 事件 |
| `projection_jobs` | 可靠写回待办：目标存储、状态、重试次数 | `(event_seq, run_id, target)` 唯一 |
| `schema_migrations` | 结构迁移登记 | `version` 主键，与 `PRAGMA user_version` 一致 |

说明：`runs`/`nodes`/`attempts`/`artifacts` 等表在第一阶段只建结构与约束，供阶段 3–5 写入；第一阶段实际写入的是 `conversations`、`messages`、`commands`、`events`（命令接收链路）。

**第二阶段（理解层）起**，`tasks`、`questions`、`question_targets` 开始真正写入，见 [理解层_阶段2交付报告.md](理解层_阶段2交付报告.md) §2；对应的原子操作实现在 [core/state_kernel/tasks.py](../core/state_kernel/tasks.py)（草稿修改）与 [core/state_kernel/questions.py](../core/state_kernel/questions.py)（消费答案）。

## 4. 命令接收原子操作（§3.4「接收消息」）

`receive_command` 在**同一个** `BEGIN IMMEDIATE` 短事务内完成四件事，提交后才返回回执：

1. **去重检查**：按 `(user_id, dedup_key)` 查 `commands`。命中且载荷指纹相同 → 幂等返回原命令（`accepted=False, duplicate=True`），不新增任何行；指纹不同 → 抛 `CommandConflictError`（冲突）。
2. **对话控制行**：不存在则登记（旧对话编号存 `legacy_conv_id`，台账内部另用 UUID 主键）。
3. **消息先落库**：用户原文写入 `messages`（序号取 `next_message_seq` 并推进），命令连同载荷指纹写入 `commands`（状态 `received`）。
4. **事件**：`command.received` 写入 `events`（全局自增序号）。

回执 `CommandReceipt` 含 `command_id/message_id/message_seq/accepted/duplicate`。去重键由前端生成（`chat.js` 的 `request_id`）；缺省时后端生成一次性编号，此时不具备重试去重保护。

**处理闭环**：任务线程启动前置 `processing`；线程正常结束回写 `processed`（附结果摘要），异常回写 `failed`（命令结果存完整错误，事件载荷中的错误截断至 500 字符）。命令不会永久停留在 `received`。

## 5. 对象版本号与事件序号

**版本号**（9.1 第 4 条）：`tasks`/`runs`/`questions` 的 `update_versioned` 要求调用方携带 `expected_version`；不符抛 `StaleVersionError`，禁止迟到结果覆盖新状态。更新成功版本 +1 并刷新 `updated_at`。

**事件序号**（9.1 第 5 条）：`events.seq` 为 `INTEGER PRIMARY KEY AUTOINCREMENT`，全局递增、跨重启连续；阶段 6 的 SSE 断线补发按它续传。

## 6. 结构版本号与迁移（9.1 第 6 条）

- 当前结构版本：`SCHEMA_VERSION = 2`（`PRAGMA user_version` + `schema_migrations` 双登记）。
  - v1：§3.2 全部必需表。
  - v2（第二阶段理解层）：`tasks` 增加 `label` / `origin_message_id` / `origin_command_id`；`questions` 增加 `prompt` / `answer` / `answered_at` / `superseded_by` / `origin_command_id`；新增 `questions(conversation_id, status)` 与 `question_targets(task_id)` 索引。迁移过程有测试覆盖（`tests/test_state_kernel.py` 测试组 8）。
- 新开库自动建全部表；已存在的库按 `MIGRATIONS` 列表补齐缺失版本。
- 迁移前自动把数据库文件备份到同目录（`ledger.sqlite3.bak-v<目标版本>-<时间戳>`）；每个迁移在单个事务内原子应用，失败回滚不留半套表。
- 程序遇到高于自身支持版本的库会拒绝打开（防止旧程序损坏新库）。
- 以后改表结构的规则：`SCHEMA_VERSION` +1，在 `MIGRATIONS` 末尾追加一条 `(版本, 说明, DDL)`，不直接改历史 DDL。

## 7. 与旧链路的关系（本阶段边界）

本阶段不改编排行为：`chat_start` 原有的 JSON 历史文件、Agent 线程、SSE 流全部照旧；状态内核并行落账。台账写入失败时旧链路继续可用（服务端打印 `[state_kernel]` 日志留痕），但去重保护随之失效——这是有意的降级策略，避免台账故障阻断生产。科学主链（数据获取/预处理/TTRI/RF/TCR/导出/评价/填洞）零改动。
