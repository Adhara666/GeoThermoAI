## 1. 这一阶段做了什么

改动的核心是一句话：**模型只提建议，程序做决定。**

改动前，Planner 直接生成可执行计划，还有一层关键词硬规则凌驾于模型理解之上（「看到有图就当填洞」「猜不到就下载」）。改动后：

```
用户消息
  → 候选理解器：模型只输出受限枚举里的候选操作（不含计划、路径、代码）
  → 程序绑定：地名 → 真实边界文件（含内容指纹）；指称 → 台账里的任务
  → 程序解析：时间按消息接收时刻 + 用户时区的锚点算成绝对区间
  → 程序校验：按能力检查必需信息，缺什么问什么
  → 信息齐全 → 登记任务并交执行链；信息不全 → 追问落台账，线程立刻释放
```

### 1.1 对照 9.2 的七条工作内容

| 9.2 要求 | 落点 | 说明 |
|---|---|---|
| 1. Planner 拆成候选理解器，只输出受限候选操作 | [operations.py](../core/agent/understanding/operations.py) / [prompts.py](../core/agent/understanding/prompts.py) / [understander.py](../core/agent/understanding/understander.py) | 10 类操作、7 种能力、6 个槽位字段的封闭枚举；枚举外内容判无效；最多一次格式修复。格式说明见 [候选操作格式说明.md](候选操作格式说明.md) |
| 2. 目标绑定，绑不唯一就追问 | [binding.py](../core/agent/understanding/binding.py) | 研究区**先收全部候选再判唯一**并记 SHA-256 内容指纹；任务支持「明确编号 → 序号 →地区/标签 → 唯一未完成任务」四级绑定；歧义一律追问，不按「最近修改」猜 |
| 3. 时间以消息接收时间为锚，单日不扩月，模糊先问 | [timeparse.py](../core/agent/understanding/timeparse.py) | 复用 `slots.parse_time_expression()`，在外层加锚点与单日保护；锚点日期、时区、原表达随槽位存档，重跑不重新解释 |
| 4. 否定与清除；默认值不得记成用户原话 | [slotbook.py](../core/agent/understanding/slotbook.py) | 每个槽位存值 + 来源 + 是否确认 + 证据；「不是武汉」留下否定记录，**只有用户在本轮原句里重新提到才能撤销**；默认值来源恒为 `default`、`confirmed=False` |
| 5. 持久问题：落台账、绑版本、一次消费、文字与卡片同入口 | [questions.py](../core/state_kernel/questions.py) / [answers.py](../core/agent/understanding/answers.py) / [service.py](../core/agent/understanding/service.py) | 问题写 SQLite 并绑定目标任务版本；答案一次消费；任务版本一变旧卡片自动失效；`/api/kernel/answer` 与文字回答共用同一套消费逻辑 |
| 6. 等待不再阻塞线程 | [service.py](../core/agent/understanding/service.py) + `server.chat_start` | 理解层需要追问时**当场返回并释放线程**，问题只存在于台账里；服务重启后问题原样还在（见 §3 重启验收）。执行阶段的审批等待仍由旧机制承担，属阶段 4 范围，见 §5 |
| 7. 失败兜底与 Chat 权限边界 | [understander.py](../core/agent/understanding/understander.py) / [resolution.py](../core/agent/understanding/resolution.py) | 模型超时或输出无效 → 如实说明、保留已确认信息、**不建任务不追问**，不用默认城市/整月/下载兜底；Chat 模式在代码层面剔除全部生产类候选，不是靠提示词 |

### 1.2 顺带修掉的两个既有缺陷

开发过程中被端到端测试逼出来的，都是真实问题，不是为通过测试而改：

1. **台账读连接不能跨线程使用**：阶段 1 的 `StateStore` 读连接在构造线程里创建，聊天任务线程读它会直接抛 `SQLite objects created in a thread can only be used in that same thread`。改为读连接开 `check_same_thread=False`（写连接不开，单一写入者仍靠线程独占保证），并补了跨线程读的回归测试。
2. **占线被拒的命令永久停在「已接收」**：`chat_start` 先把命令落库、再检查「该对话已有任务在执行中」并返回失败，命令就再也拿不到终态，违反 §3.4 的处理闭环约定。新增 `mark_command_rejected`，拒绝路径写 `rejected` 终态并记事件。

### 1.3 与执行链的接缝

阶段 2 **不编译节点图、不实现调度**（那是阶段 3、4）。理解层确认后的任务通过 [execplan.py](../core/agent/understanding/execplan.py) 翻译成现有执行链认得的 plan 形状，`PlannerAgent.run_resolved()` 据此直接出计划，跳过「意图分类 + 槽位合并 + 研究区解析」——模型不再有第二次改写机会，关键词分流也不再有机会劫持意图。确定性规则 P1–P7 保留为安全网。

整体开关：`settings.agent.understanding_enabled`（默认 true），关掉即整体回退到旧的「Planner 直接出计划」路径。

### 1.4 新增接口

| 接口 | 用途 |
|---|---|
| `GET /api/kernel/session?project=&conv=` | 会话快照：本对话的任务卡（地区/时间/产品方式/状态/否定记录）与待答问题 |
| `POST /api/kernel/answer` | 回答一条持久问题（卡片点击入口，与文字回答同一套消费逻辑） |
| SSE `tasks` 事件 | 理解层写完台账后推送任务卡快照；前端未监听时自动忽略 |

## 2. 台账扩展（schema v1 → v2）

阶段 1 只建了 `tasks` / `questions` 的表骨架，阶段 2 开始真正写入，补了几个字段并加了查询索引。走的是阶段 1 定下的**带备份迁移**流程：`SCHEMA_VERSION` +1、在 `MIGRATIONS` 末尾追加，不改历史 DDL。

| 表 | 新增 | 用途 |
|---|---|---|
| `tasks` | `label`、`origin_message_id`、`origin_command_id` | 任务卡中文标签 + 溯源到原始消息（§5.2「任务最少保存…原消息」） |
| `questions` | `prompt`、`answer`、`answered_at`、`superseded_by`、`origin_command_id` | 问题正文与答复必须落库，答案才谈得上「一次消费」 |
| 索引 | `questions(conversation_id, status)`、`question_targets(task_id)` | 查开放问题、按任务失效旧问题 |

迁移本身有测试覆盖（[tests/test_state_kernel.py](../tests/test_state_kernel.py) 测试组 8）：造一个只有 v1 结构的旧库，打开后自动迁移，验证新列补齐、迁移登记表有记录、迁移前自动生成 `.bak-v2-*` 备份、迁移后照常收命令。

## 5. 已知边界与留给后续阶段的事

如实写清楚，避免验收时产生错误预期：

1. **执行中的对话仍然只能跑一件事**。理解层能一次登记两个任务，但没有调度器，所以第一个任务进执行链后，同一对话的新消息会被明确拒绝（并写 `rejected` 终态）。「武汉在算、南京同时下载」「中途改需求」属于 9.4 阶段 4「调度与执行」。
2. **执行阶段的审批等待仍在阻塞线程**。9.2 第 6 条要求的「等待不阻塞」，在理解层已经完全做到（追问当场返回、问题落台账、重启不丢）；但 `RoleHooks._ask()` 那条链路的改造，总体方案 §6.1 写明需要调度器承接（「调度器存问题并结束本次执行…答案到达再派发相应决定节点」），因此留在阶段 4。本阶段的处理是**不动它**，避免在没有恢复机制的情况下把执行链改成一去不返。
3. **任务状态还是粗粒度**。`_settle_task` 只能从执行链的返回文本区分「等待用户 / 失败 / 完成」，因为还没有节点级状态（阶段 3、4）。
4. **参数快照尚未冻结**。理解层把已确认参数直接交给执行链，排队期间改设置界面是否影响已提交任务，要等阶段 3 的参数快照。
5. **前端还没有任务卡界面**。后端已经提供 `GET /api/kernel/session` 与 SSE `tasks` 事件，前端渲染是 9.6 阶段 6 的事。
6. **回归基线建议重新登记**。2026-08-14 那份登记值已经无法用远程数据源复现，建议把这次下载的 raw 与 provenance 冻结保存作为后续阶段的对照基准。
